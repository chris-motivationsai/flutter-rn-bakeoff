# Bakeoff slice: "Log an observation three ways"

One small mobile slice, built twice (Flutter, React Native), judged by the same neutral judge.
The kit in this folder is read-only. If something in it looks wrong, write it in your `KIT-ISSUES.md` and keep going; do not bend your code to a result that contradicts this spec.

## 1. What the slice is

A person logs health observations in a life-stage app. The same code builds two apps, **Polly** and **Premom**, from a stage pack (`packs/*.json`). The pack is data: it decides which observation types exist, how a strip result is worded, and what can be bought. No app name or type list may be hard-coded.

Observations arrive three ways:

1. **Manual** entry.
2. **Strip reader**: a photo of a test strip goes through the C++ engine in `engine/` and becomes an `lh` observation.
3. **Thermometer**: a Bluetooth basal thermometer sends a temperature that becomes a `bbt` observation.

Everything is logged offline first, stored on the device, and synced later. A store purchase unlocks one thing: the numeric LH result in Premom.

## 3. Data rules

**Timestamps** are UTC with second precision and no milliseconds: `2026-11-03T06:45:00Z`. The server rejects anything else.

**Observation** (see `ObservationBody` / `Observation` in the contracts):

- `id`: UUID generated by the client.
- `type`, `value`: `bbt` → `{celsius}` rounded to 2 decimals; `lh` → `{ratio}` rounded to 3 decimals; `flow`, `mucus` → `{code}`.
- `observedAt`, `source` (`manual` | `strip_reader` | `thermometer`).
- `reader`: for `strip_reader` exactly `{engineVersion}` (from `strip_engine_version()`); for `thermometer` exactly `{deviceModel}` (the device name); absent for `manual`.

The clock is injected: "now" is the `at` of the step being run. Never read the system clock for behaviour.

### Manual log
Check in this order: type not in the pack catalog → `unknown_type`; `manual` not in the entry's `sources` → `source_not_allowed`; value outside `min`/`max` or not one of `values` → `invalid_value`. `observedAt` is the step's `at`.

### Strip reader
The image is a binary PGM (`P5\n<width> <height>\n255\n` then width×height gray bytes). Pass the gray bytes to `strip_read`.

- Status 1 → `strip_no_control_line`, 2 → `strip_too_dark`, 3 → `strip_too_bright`. **A failed read creates nothing.** It is never recorded as a low result.
- Status 0 → an `lh` observation with `ratio` rounded to 3 decimals.
- The level shown is the pack level with the highest `minRatio` that is ≤ the ratio. The level is computed for display; it is not stored.
- Numeric display: if the pack's `numeric` is `null`, the ratio is never shown (`ratio: null, locked: false`). If it names an entitlement, the ratio is shown only while that entitlement is active (`locked: false`), otherwise `ratio: null, locked: true`.

### Thermometer
A session fixture is a script of Bluetooth events: `connect`, `notify` (`char`, `hex`), `disconnect`. The device follows the Bluetooth Health Thermometer service (0x1809):

- `2A1C` is the final Temperature Measurement. `2A1E` is an intermediate reading and must be ignored.
- Frame: flags byte, then an IEEE-11073 32-bit FLOAT (24-bit signed mantissa, little-endian, then a signed 8-bit exponent; value = mantissa × 10^exponent). Flags bit 0: 1 = Fahrenheit. Bit 1: a 7-byte timestamp follows (year uint16 LE, month, day, hour, minute, second; treat as UTC). Bit 2: a 1-byte temperature type follows.
- Mantissa `0x7FFFFF` (NaN) or a frame too short to hold the fields its flags declare → `thermo_invalid_reading`.
- No `2A1C` before disconnect → `thermo_no_final_reading`.
- Convert Fahrenheit to Celsius, round to 2 decimals. Outside the pack's `bbt` `min`/`max` → `thermo_invalid_reading`.
- `observedAt` is the device timestamp when present, otherwise the step's `at`.

### Edit and delete
Target is found by `{type, observedAt}` among observations this pack can show. Not there → `not_found`. Edit of a non-manual observation → `read_only` (reader results are never edited). Bad value → `invalid_value`. Delete is allowed for any source.

## 4. Offline store and sync

All state must be stored durably on the device: observations, pending changes, the pull cursor, conflicts, entitlements and unverified receipts. A `restart` step disposes the app and opens a new instance on the same storage; nothing durable may be lost.

**Pending changes.** At most one pending mutation per observation. A new local change to an observation that already has one replaces it. A `mutationId` is created when the change is made, stored, and reused on every retry. Creating and deleting an observation before it was ever sent sends nothing. Pending mutations are sent oldest first, ordered by when the observation became pending.

**`sync` does, in order:**

1. Try to verify any held receipts (section 5).
2. Push pending mutations to `POST /v1/sync/push`, at most 20 per request. Do not send an empty push.
3. Pull with `GET /v1/sync/pull?since=<cursor>` and store the new cursor.

Any transport failure or non-2xx answer in step 2 or 3 ends the sync with `network`. What was confirmed before the failure stays confirmed; everything else stays pending.

**Push results**, per mutation:

- `applied` or `duplicate`: done. Remember `revision` as the observation's base revision. (`duplicate` means the server already applied this `mutationId`.)
- `conflict`: **the server copy wins.** Replace the local observation with `server` (or remove it locally if `server.deleted`), drop the mutation, and append `{type, observedAt}` to a durable conflicts list.

**Pull**: apply each change unless that observation has a pending local mutation. `deleted: true` removes it locally. Observations of a type the pack does not have must be kept in storage but never shown, and never edited or deleted from this app.

## 5. Purchases and entitlements

The store is behind an adapter. In scenarios the fake store plays the step's `store` script in order:

- `pending` → `purchaseState` becomes `pending`.
- `cancelled` → step result `cancelled`. This is not an error: `lastPurchaseError` stays `null`.
- `error` → step result and `lastPurchaseError` are `store_error`.
- `purchased {txId, receipt}` → store the receipt durably, then call `POST /v1/entitlements/verify`.
  - 200 → save the returned entitlements, then `finish(txId)` on the store.
  - 422 → discard the receipt, `finish(txId)`, grant nothing. Step result and `lastPurchaseError` are the server's `error` code.
  - Unreachable (transport failure or any other status) → keep the receipt, `purchaseState` is `verifying`, step result is ok. Never unlock before the server says yes.

If the pack has no such product: `not_available`, and the store is never called.

`restore` plays a list of `{txId, receipt}`: each is handled like `purchased`. The step result is ok; a refused receipt sets `lastPurchaseError`.

Held receipts are retried at the start of every `sync`. A refusal there sets `lastPurchaseError`.

An entitlement is active while `expiresAt` > now (the step's `at`). It keeps working offline until then.

`purchaseState` is `verifying` while any receipt is held, else `pending` after a `pending` event with nothing following, else `idle`. `lastPurchaseError` is reset at the start of every `purchase` and `restore` step. After a restart, `pending` becomes `idle` and `lastPurchaseError` is `null`; `verifying` survives.

## 6. Analytics gate

After each observation is **created** on this device, send one `POST /v1/events` with exactly `{name: "observation_logged", props: {type, source, pack}}`. One attempt, awaited, dropped silently on failure. No health value may appear in it; the server counts any extra field as a violation.

## 7. Server

All app endpoints need `Authorization: Bearer test-token` and JSON bodies. Shapes are in `contracts/schemas.ts`.

| Endpoint | Notes |
|---|---|
| `POST /v1/sync/push` | 413 if more than 20 mutations. |
| `GET /v1/sync/pull?since=N` | |
| `POST /v1/entitlements/verify` | 200 or 422. |
| `POST /v1/events` | 202, or 422 on a violation. |
| `POST /__control` | Test control. Your runner forwards `server_control` step bodies here verbatim and never interprets them. |

The server can be made unreachable (connection dropped), made to answer 503, or made to apply a push and then drop the connection without answering.

## 8. Runner contract

Provide an executable `run-scenario.sh` in your stack folder:

```
./run-scenario.sh <scenario.json> <serverUrl> <out.json> <workDir>
```

- `scenario.json`: `{id, pack, user, steps[], expect}`. Fixture paths in steps are relative to the scenario file's folder. Never read `expect`.
- `workDir`: an empty folder for the app's storage.
- Run every step in order through the same app core your screens use. Exit 0 when the run finished, even if steps failed.
- Write `out.json`: `{"steps": [{"ok": true} | {"ok": false, "error": "<code>"}, …], "snapshots": {"<name>": Snapshot}}`, one step result per step.

**Steps:** `log_manual {type, value}`, `scan_strip {type, image}`, `thermometer_session {type, script}`, `edit {target, value}`, `delete {target}`, `sync`, `restart`, `purchase {productId, store}`, `restore {store}`, `server_control {body}`, `snapshot {name}`. Every step has `at`. `server_control`, `restart` and `snapshot` always return ok.

**Snapshot** (what the Today screen would show):

```json
{
  "pack": "premom",
  "observations": [
    { "type": "lh", "observedAt": "…", "source": "strip_reader", "sync": "pending" | "synced",
      "display": { "level": "high", "ratio": 0.689, "locked": false } }
  ],
  "pendingMutations": 2,
  "conflicts": [ { "type": "flow", "observedAt": "…" } ],
  "entitlements": ["premium"],
  "purchaseState": "idle" | "pending" | "verifying",
  "lastPurchaseError": null,
  "storeFinished": ["tx-…"]
}
```

- `observations`: only types in the pack, not locally deleted, sorted by `observedAt` then `type`. `display` for `bbt`/`flow`/`mucus` is the stored value object.
- `pendingMutations`: number of pending mutations, deletes included.
- `conflicts`: in the order they happened.
- `entitlements`: names active at the step's `at`, sorted.
- `storeFinished`: every `txId` finished on the store since the scenario began, sorted (the fake store outlives restarts).

## 9. What the judge checks

For every scenario: each step result, each snapshot, the server's final observations and deletions, the number of analytics events, zero analytics violations, zero oversize pushes and zero rejected mutations.
