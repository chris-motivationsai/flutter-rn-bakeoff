# The five hard parts: phone path vs tested path

Nothing in this project has run on a phone or simulator. "Tested" below means: ran on this Mac, under Node 26
(Jest, the scenario runner) unless stated otherwise.

| Hard part | What a phone would run | What the tests and `run-scenario.sh` actually run | Not verified on this machine |
|---|---|---|---|
| **C++ engine** | JS `core/app.ts` → `adapters/real/nativeStripEngine.ts` → Expo module `modules/strip-engine` (iOS: `StripEngineModule.swift`; Android: `StripEngineModule.kt` → `strip_jni.cpp`) → `cpp/strip_bridge.cpp` → `strip_engine.cpp` (byte-identical copy of `kit/engine`, built by `StripEngine.podspec` / `CMakeLists.txt`). | Same `core/app.ts` → `adapters/fake/nodeStripEngine.ts` → N-API addon `node/strip_napi.cpp` → the **same** `cpp/strip_bridge.cpp` → `kit/engine/strip_engine.cpp` compiled straight from the kit. Addon results are compared with the kit's own CLI on all 106 strip fixtures. The Android JNI file `strip_jni.cpp` is additionally compiled and **run on a host JVM** (Homebrew openjdk 17) through a Java stand-in class with the Kotlin module's exact name and native signatures, and compared with the addon on all fixtures (`tests/core/jni.test.ts`; skipped if no JDK). Expo autolinking resolving the module for iOS and Android is checked in `check.sh`. | The Swift module, the Kotlin module, the podspec, `build.gradle` and `CMakeLists.txt` have never been compiled (no Xcode, no Android SDK/NDK). Whether Expo's `Uint8Array` argument conversion and `rawPointer` / `toDirectBuffer()` behave as I read them in the SDK 58 sources. ARM/Android floating-point results vs this Mac's (ratios are rounded to 3 decimals, so a difference is unlikely but unproven). |
| **Bluetooth** | `adapters/real/blePlxThermometer.ts` (react-native-ble-plx 3.5: permissions, scan for service 0x1809, connect, monitor 2A1C and 2A1E, base64 → bytes, disconnect) → `core/thermometer.ts` (frame decoding, session rules) → `core/app.ts`. | Scenarios and core tests: `adapters/fake/fakes.ts` `FakeThermometer` plays the fixture script into the **same** `core/thermometer.ts` and `core/app.ts`. Separately, `tests/device/blePlxThermometer.test.ts` runs the **real adapter** with the library's `BleManager` class replaced by a scripted one (the library's real `fullUUID` is used), including one end-to-end reading into the core. The adapter type-checks against the library's real typings. | Everything inside react-native-ble-plx and below: real scanning, pairing, permissions dialogs, indications on 2A1C, timing, reconnects, a real thermometer's device name and frames. The adapter picks the first device advertising 0x1809; there is no device picker. The mock found one real bug (state listener firing synchronously); a device would probably find more. |
| **Storage** | `core/storage.ts` (all SQL, schema, transactions) → `adapters/real/expoSqlite.ts` (4 one-line calls into expo-sqlite's synchronous API). | The **same** `core/storage.ts` → `adapters/fake/nodeSqlite.ts` (4 one-line calls into Node's built-in `node:sqlite`), on a real file in the work dir; `restart` closes it and opens a new `AppCore` on the same file. `tests/device/expoSqlite.test.ts` runs `Storage` through the real expo adapter with expo-sqlite mocked by Node SQLite behind the same method names. | expo-sqlite itself: that `execSync` accepts the multi-statement schema, `ON CONFLICT ... DO UPDATE` / `AUTOINCREMENT` behave the same in its bundled SQLite, the type of `COUNT(*)`/integer columns it returns, file location and durability across a real process kill. Synchronous calls on the JS thread are fine for this data size but were not measured. |
| **Sync** | `core/sync.ts`, `core/api.ts` → `adapters/fetchHttp.ts` → the global `fetch` (on a phone that is Expo's native `expo/fetch`). | The **same** `core/sync.ts`, `core/api.ts` and `adapters/fetchHttp.ts` → Node's `fetch`, against the kit's real test server (down, 503, apply-then-drop, remote edits). The UI tests use a `node:http` transport instead, because jest-expo replaces `fetch` with a stub. | Expo's `fetch` implementation: how it reports a dropped connection, whether `AbortController` timeouts work the same, behaviour when the app is backgrounded mid-request. No background sync or connectivity listener exists; sync happens when the user presses Sync. |
| **Store purchases** | `core/purchases.ts` → `adapters/real/iapStore.ts` (react-native-iap 17: `initConnection`, `requestPurchase`, purchase/error listeners, `getAvailablePurchases`, `finishTransaction`). The receipt sent to the server is the library's `purchaseToken`. | Scenarios and core tests: `FakeStore` plays the step's store script into the **same** `core/purchases.ts`, verifying against the kit server. `tests/device/iapStore.test.ts` runs the **real adapter** with the library's functions mocked (event mapping, listener cleanup, finish after restart). The adapter type-checks against the library's real typings. | Everything about real stores. Known gaps: products are requested as `type: 'subs'` (the pack does not say), and on Android a subscription purchase needs an offer token from `fetchProducts`, which the adapter does not fetch, so a real Play purchase would probably fail. Purchases that complete while the app is closed (Ask to Buy, pending payments) are only picked up by Restore. StoreKit/Play sandbox behaviour, the `ErrorCode` values the library really emits (the test hard-codes three of them), and a real server-side receipt format are all unverified. |

## Also unverified

- The screens have rendered only in Jest (`@testing-library/react-native`). No layout, keyboard, safe-area or
  navigation behaviour has been seen on a screen.
- The camera path: `expo-camera` capture → `expo-image-manipulator` resize → PNG → `pngToGray`. Only `pngToGray`
  is tested. The engine expects a pre-cropped strip; nothing finds or crops the strip in the photo.
- The JS bundle builds for iOS and Android (`expo export`, Hermes bytecode, in `check.sh`) and `expo prebuild
  --no-install` generated both native projects with the pack's app name and permission texts (run once by hand,
  output deleted). The bundle has never been executed by Hermes, and no native project has been compiled.
- An EAS cloud build would not see `../kit` (packs and contracts are outside the project folder).
