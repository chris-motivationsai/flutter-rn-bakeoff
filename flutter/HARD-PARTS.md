# The five hard parts

Nothing in this folder has run on a phone, a simulator, or as a compiled iOS/Android app. "Tests" below means `./test.sh` (`flutter test`, Dart VM on macOS arm64); "runner" means `run-scenario.sh` (`dart run`, same VM).

| Hard part | Code a phone would run | Code the tests and the scenario runner actually run | Unverified on this machine |
|---|---|---|---|
| **C++ engine** | `kit/engine/strip_engine.cpp`, unmodified, compiled for the target by the build hook `hook/build.dart` (`native_toolchain_c`) and bundled as a native code asset; called through Dart FFI `@Native` bindings in `lib/core/engine/strip_engine_ffi.dart` by `NativeStripEngine`. | The same: same hook, same C++ source, same `@Native` bindings, same `NativeStripEngine`, compiled for macOS arm64. Tests compare its status and ratio with the kit's `strip_cli` on 36 public fixtures. Only the image source differs (PGM file instead of camera). | The hook has only ever compiled for macOS. iOS and Android cross-compiles (Xcode / NDK toolchains), bundling in an `.ipa`/`.apk`, and symbol lookup on device are untested. The camera adapter (`image_picker`) is analyzed only; its decode-to-grayscale step is unit-tested, the picker call is not. Cropping a strip out of a real photo is not implemented: the whole photo is passed to the engine, which expects a pre-cropped strip. |
| **Bluetooth** | `lib/adapters/real/ble_thermometer.dart` (`flutter_blue_plus` 2.3.15): scan for service 0x1809, connect, subscribe to 2A1C and 2A1E, forward as `BleEvent`s. Then `lib/core/thermometer.dart` (frame parsing, final-reading rule) and `AppCore.thermometerSession`. | `lib/adapters/fake/fakes.dart` `ScriptedThermometer` replays the fixture as the same `BleEvent`s. Everything after the adapter (`thermometer.dart`, `AppCore.thermometerSession`) is the phone's code. | The whole real adapter: it passes `flutter analyze` against the plugin's API and has never executed. Scanning, permissions prompts, connection timing, indication vs notification subscription, whether the plugin reports 16-bit UUIDs as `2A1C` the way the adapter assumes (`Guid.str`), behaviour with a real thermometer. `flutter_blue_plus` 2.x also requires a paid licence for commercial use (`License.commercial` is passed in `main.dart`). |
| **Storage** | `lib/core/storage.dart` on `package:sqlite3` 3.9.1 (SQLite through FFI; the package's build hook bundles the SQLite library). File location from `path_provider` in `lib/adapters/real/device_storage.dart`. | The same `storage.dart`, same package, same SQL, on a real database file in the work dir / a temp dir; `restart` closes the database and reopens the file. Only the directory lookup differs. | `path_provider` call (analyzed only). That the sqlite3 hook bundles correctly for iOS/Android. Behaviour when the OS kills the app mid-write (transactions are used, but no crash test was run). No encryption at rest, though the data is health data. |
| **Sync** | `AppCore.sync` / `_push` / `applyPull` in `lib/core/app_core.dart` and `lib/core/api.dart` on `package:http`. | The same code. The runner and `test/scenarios_test.dart` talk real HTTP to the kit's node server on 127.0.0.1; unit and widget tests swap the transport for `http`'s `MockClient` wired to an in-process fake server. | Real networks: TLS, slow or half-open connections (there is a 15 s per-request timeout, never triggered in tests), background execution limits, auth beyond the fixed test token. Nothing schedules a sync automatically; the user taps Sync. |
| **Store purchases** | `lib/adapters/real/store_billing.dart` (`in_app_purchase` 3.3.1): maps the plugin's purchase stream to `StoreEvent`s, completes transactions on `finish`. Then `AppCore.purchase` / `restore` / receipt holding and verification. | `lib/adapters/fake/fakes.dart` `FakeStore` plays the scripted events. Everything after the adapter (hold receipt, verify, grant, finish, retry on sync, expiry) is the phone's code. | The whole real adapter: analyzed against the plugin API, never executed. Product lookup in App Store Connect / Play Console, sandbox purchases, what `serverVerificationData` contains on each store and whether a real server could verify it, restore completion (the adapter waits a fixed 2 s for restored purchases because the plugin gives no end marker), purchases that are approved later (handled by a callback that has never fired). |

## Static checks against the real plugins

`./check.sh` runs `flutter analyze` over `lib/adapters/real/` with these resolved versions: `flutter_blue_plus` 2.3.15, `in_app_purchase` 3.3.1, `image_picker` 1.2.4, `image` 4.12.0, `path_provider` 2.1.6, `sqlite3` 3.9.1, `http` 1.6.0, `native_toolchain_c` 0.19.6, `hooks` 2.2.0. No issues.

## Device build configuration present but never built

- `hook/build.dart`: engine build for any target.
- `ios/Runner/Info.plist`: Bluetooth, camera and photo-library usage strings.
- `android/app/src/main/AndroidManifest.xml`: Bluetooth and internet permissions.
- Pack selection by `--dart-define=PACK=…`. Separate bundle ids, icons and store listings per app (flavors) are not set up.
